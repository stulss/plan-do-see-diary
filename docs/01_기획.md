## 2. 무엇으로 붙이는가 (T07-C91 / C92)

로그인 방법을 **세 가지** 제공한다: 이메일+비밀번호 · 구글 · 카카오.

| 구분 | 선택 | 이름 / 버전 |
|---|---|---|
| 전체 방식 | **직접 구현(자체 세션)** + 검증된 라이브러리 조합 | — |
| 비밀번호 해시 | 라이브러리 위임 | **bcryptjs** (설치 버전 고정) — 작업 계수 12 |
| 소셜 로그인 | 라이브러리 위임 | **openid-client** v6.x — PKCE·state·id_token 서명 검증 내장 |
| 소셜 제공자 | OpenID Connect 로 통일 | 구글 `accounts.google.com`, 카카오 `kauth.kakao.com` |
| 세션 토큰 | Node 표준 라이브러리 | `node:crypto` 의 `randomBytes(32)` / `createHash("sha256")` |
| 세션 보관 | 서버 DB `user_session` 표 | — |
| 세션 전달 | `HttpOnly; Secure; SameSite=Lax; Path=/` 쿠키 | — |

**핵심**: 구글·카카오로 들어와도 **로그인 상태를 유지하는 것은 우리 세션**이다. 제공자의 토큰은 신원 확인에 한 번 쓰고 버린다.
그래서 소셜 로그인이어도 **로그아웃 즉시 무효화(T07-C114)** 가 똑같이 성립한다.

### 2-1. 왜 비밀번호 로그인을 없애지 않는가

카드 2(T07-C101 ~ C107)는 **저장된 비밀번호의 모습**과 **같은 비밀번호로 만든 두 계정의 저장값이 다름**을 증거로 요구한다.
소셜 로그인만 쓰면 비밀번호 자체가 없어 이 증거를 만들 수 없다. 따라서 이메일+비밀번호 로그인을 **유지**하고 소셜을 추가한다.

## 3. 왜 그것을 골랐는가 (T07-C93 / C102)

### 3-1. 함께 검토했지만 고르지 않은 방법

| 검토한 방법 | 고르지 않은 이유 |
|---|---|
| **Auth.js(NextAuth) v5** | 소셜만 쓰면 DB 세션이 가능하지만, **Credentials(비밀번호) Provider 를 함께 쓰는 순간 세션 전략이 JWT 로 고정**된다. JWT 는 서버에 상태가 없어 로그아웃해도 만료 전까지 유효하므로 **T07-C114** 를 만족시킬 수 없다. 비밀번호 로그인을 포기할 수 없으므로(2-1 참조) 배제 |
| **Supabase Auth** | 로그아웃 뒤에도 액세스 토큰이 만료 전까지 유효해 "같은 값으로 다시 요청 → 거절" 장면을 만들 수 없다. 과제 6의 원시 SQL 접근 계층을 RLS 로 전부 새로 써야 하는 비용도 크다 |
| **arctic** (소셜 로그인 전용 클라이언트) | 자체 세션과 조합하기 좋은 후보였으나 **2026년 7월 지원 중단**되어 새로 도입하지 않는다 |
| **OAuth 흐름 직접 구현(raw fetch)** | state·PKCE·id_token 서명 검증을 직접 짜야 한다. 보안 경로에 자체 코드를 늘리지 않는다는 이 프로젝트의 원칙에 어긋난다 |
| **express-session 계열** | Next.js App Router 는 Express 미들웨어 스택을 쓰지 않아 어댑터 비용이 세션 표 하나보다 크다 |

### 3-2. 해시 방법으로 bcrypt 를 고른 이유 (T07-C102)

bcrypt 는 **계정마다 무작위 소금값(salt)을 자동으로 만들어 해시 문자열 안에 함께 담기 때문에**, 같은 비밀번호로 만든 두 계정의 저장값이 반드시 서로 달라지고(T07-C104) 소금값 관리 코드를 직접 쓸 필요가 없다. `bcryptjs` 는 순수 자바스크립트라 서버리스에서 네이티브 빌드가 필요 없다.

| 검토한 다른 해시 방법 | 고르지 않은 이유 |
|---|---|
| `node:crypto` 의 scrypt | 소금값 생성·저장 형식·상수시간 비교를 직접 작성해야 한다 |
| PBKDF2 | 같은 이유에 더해, 같은 비용에서 GPU 병렬 공격 저항이 bcrypt 보다 약하다 |
| argon2 | 가장 권장되지만 네이티브 빌드가 필요해 서버리스 배포 실패 위험이 있다 |
| SHA-256 1회 | 소금값이 없고 너무 빨라 사전 공격에 무력하다 |

### 3-3. 소셜 제공자 사전 조건

| 제공자 | 준비할 것 |
|---|---|
| 구글 | Google Cloud Console 에서 OAuth 클라이언트 생성, 승인된 리디렉션 URI 등록 |
| 카카오 | 카카오 디벨로퍼스 앱 생성, **카카오 로그인 > OpenID Connect 활성화**, Redirect URI 등록, Client Secret 발급 |

> **카카오 이메일 주의**: `account_email` 동의항목은 **비즈 앱 전환 + 비즈니스 정보 심사(영업일 3~5일)** 를 거쳐야 쓸 수 있다.
> 심사 전에는 카카오가 이메일을 주지 않으므로 **이메일 없이도 계정이 만들어져야 한다**(4-1, 4-2 참조).

## 4. 데이터 모델 변경

### 4-1. 새로 만드는 표 (`schema_auth.sql`)

```sql
-- 계정.
-- login_id / email / password_hash 를 NULL 허용으로 둔다.
-- 소셜 전용 계정은 아이디와 비밀번호가 없고, 카카오는 이메일을 주지 않는 경우가 있기 때문이다.
-- 비밀번호 로그인은 login_id 와 password_hash 가 둘 다 채워진 계정에서만 가능하며,
-- 이 조건은 애플리케이션이 확인한다.
-- nickname 은 모든 계정에 반드시 있고 서로 겹칠 수 없다.
CREATE TABLE app_user (
  id            bigserial PRIMARY KEY,
  login_id      text CHECK (login_id IS NULL OR btrim(login_id) <> ''),
  nickname      text NOT NULL CHECK (btrim(nickname) <> ''),
  email         text CHECK (email IS NULL OR btrim(email) <> ''),
  password_hash text,                   -- bcrypt 해시. 원문은 어디에도 저장하지 않는다.
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
-- 아이디·닉네임·이메일은 대소문자를 무시하고 중복될 수 없다 (T07-C98).
-- 화면의 중복확인은 편의일 뿐이고, 실제로 막는 것은 이 세 인덱스다.
CREATE UNIQUE INDEX app_user_login_id_key ON app_user (lower(login_id)) WHERE login_id IS NOT NULL;
CREATE UNIQUE INDEX app_user_nickname_key ON app_user (lower(nickname));
CREATE UNIQUE INDEX app_user_email_key    ON app_user (lower(email))    WHERE email IS NOT NULL;

-- 소셜 계정 연결. 한 사람이 구글과 카카오를 모두 붙일 수 있다.
CREATE TABLE user_identity (
  provider         text   NOT NULL CHECK (provider IN ('google', 'kakao')),
  provider_user_id text   NOT NULL,     -- id_token 의 sub. 제공자 안에서 고유하다.
  user_id          bigint NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
  email_at_link    text,                -- 연결 시점에 제공자가 준 이메일(없을 수 있다)
  created_at       timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (provider, provider_user_id)
);
CREATE INDEX user_identity_user_idx ON user_identity (user_id);

-- 세션. 쿠키에는 난수 원문이, 이 표에는 그 값의 SHA-256 해시만 들어간다.
-- DB가 통째로 유출돼도 저장된 값만으로는 남의 세션을 흉내 낼 수 없다.
CREATE TABLE user_session (
  token_hash text   PRIMARY KEY,        -- sha256(쿠키 원문) 64자 hex
  user_id    bigint NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
  expires_at timestamptz NOT NULL,      -- 발급 시각 + 7일 (T07-C111)
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX user_session_user_idx ON user_session (user_id);
```

### 4-2. 계정 연결 규칙

소셜 로그인 콜백에서 `(provider, sub)` 로 `user_identity` 를 찾는다.

| 상황 | 처리 |
|---|---|
| 이미 연결된 신원 | 그 계정으로 세션 발급 |
| 처음 보는 신원 + **제공자가 인증된 이메일을 줌** + 그 이메일의 계정이 있음 | 그 계정에 신원을 연결 |
| 처음 보는 신원 + 이메일이 없거나 **인증되지 않음** | **새 계정을 만든다.** 자동 연결하지 않는다 |
| 이미 로그인한 상태에서 소셜 연결 | 현재 로그인한 계정에 연결 |

> 인증되지 않은 이메일로 기존 계정에 자동 연결하면, 남의 이메일을 주장해 계정을 가로챌 수 있다.
> 그래서 **`email_verified` 가 참일 때만** 연결한다.

**소셜 계정의 닉네임**: 제공자가 준 닉네임을 그대로 쓰되, 이미 있는 닉네임이면 뒤에 숫자를 붙여 비어 있는 것을 찾는다(`홍길동` → `홍길동2` → `홍길동3`).
제공자가 닉네임조차 주지 않으면 `사용자` + 임의 숫자로 만든다. 닉네임은 계정 화면에서 나중에 바꿀 수 있고, 바꿀 때도 중복 검사를 똑같이 거친다.
**소셜 전용 계정에는 아이디(`login_id`)를 만들지 않는다.** 나중에 비밀번호 로그인을 쓰고 싶으면 계정 화면에서 아이디와 비밀번호를 설정한다.

### 4-3. 기존 표에 소유자 붙이기 (과제 6 DB 를 함께 쓰면서)

**순서를 지켜야 과제 6 배포가 깨지지 않는다.**

```sql
-- 1) 먼저 NULL 허용으로 추가한다. 이 시점에도 과제 6 앱은 그대로 동작한다.
ALTER TABLE plan   ADD COLUMN user_id bigint REFERENCES app_user(id) ON DELETE CASCADE;
ALTER TABLE task   ADD COLUMN user_id bigint REFERENCES app_user(id) ON DELETE CASCADE;
ALTER TABLE review ADD COLUMN user_id bigint REFERENCES app_user(id) ON DELETE CASCADE;

-- 2) 소유자 계정을 화면에서 가입한 뒤, 과제 6에서 만든 기존 자료를 그 계정으로 옮긴다 (T07-C100).
UPDATE plan   SET user_id = :owner_id WHERE user_id IS NULL;
UPDATE task   SET user_id = :owner_id WHERE user_id IS NULL;
UPDATE review SET user_id = :owner_id WHERE user_id IS NULL;

-- 3) 임시 호환 장치.
--    과제 6 배포가 같은 DB에 user_id 없이 INSERT 하는 동안 소유자에게 자동 귀속시킨다.
--    PR 을 main 에 병합해 과제 6 배포가 인증판으로 바뀌면 반드시 DROP DEFAULT 한다.
ALTER TABLE plan   ALTER COLUMN user_id SET DEFAULT :owner_id;
ALTER TABLE task   ALTER COLUMN user_id SET DEFAULT :owner_id;
ALTER TABLE review ALTER COLUMN user_id SET DEFAULT :owner_id;

-- 4) 이제 NOT NULL 로 잠근다.
ALTER TABLE plan   ALTER COLUMN user_id SET NOT NULL;
ALTER TABLE task   ALTER COLUMN user_id SET NOT NULL;
ALTER TABLE review ALTER COLUMN user_id SET NOT NULL;

CREATE INDEX plan_user_idx   ON plan (user_id);
CREATE INDEX task_user_idx   ON task (user_id, due_date);
CREATE INDEX review_user_idx ON review (user_id);
```

**되돌리기**: 3)의 DEFAULT 는 PR 병합 직후 `ALTER TABLE ... ALTER COLUMN user_id DROP DEFAULT;` 로 없앤다.
과제 7 코드는 INSERT 할 때 항상 `user_id` 를 명시하므로 DEFAULT 에 의존하지 않는다.

> 과제 6 자료가 이미 같은 DB 에 있으므로 **자료를 옮기는 별도 가져오기 스크립트는 필요 없다.** 2)의 `UPDATE` 세 줄이 T07-C100 을 충족한다.

## 5. 인증 흐름과 소스 위치 (T07-C128)

| 흐름 | 지나가는 소스 |
|---|---|
| **아이디·닉네임 중복확인** | `app/(auth)/signup/page.tsx` 입력 중 → `app/api/auth/check/route.ts` → `lib/service/auth.ts` 의 `isAvailable()` → `lib/repository/user.ts` → 사용 가능 여부만 응답 |
| **가입** | `app/(auth)/signup/page.tsx` → `app/api/auth/signup/route.ts` → `lib/service/auth.ts` 의 `signUp()` → `lib/domain/rules.ts` 의 `checkPasswordRule()` → bcrypt 해시 → `lib/repository/user.ts` 의 `insert()`(유니크 위반 시 409) → `lib/repository/session.ts` 의 `create()` → `lib/dto/user.ts` |
| **로그인(비밀번호)** | `app/(auth)/login/page.tsx` → `app/api/auth/login/route.ts` → `lib/service/auth.ts` 의 `signIn()` → `lib/repository/user.ts` 의 `findByLoginId()` → bcrypt 비교 → `lib/repository/session.ts` 의 `create()` |

## 6. 접근 통제 규칙 (T07-C116 ~ C126)

1. **사용자 ID 는 오직 세션에서만 얻는다.** URL 경로·쿼리스트링·요청 헤더·요청 본문의 `user_id`, `owner`, `email` 같은 값은 **읽지 않는다** (T07-C123).
2. **한 건 조회·수정·삭제**는 `WHERE id = $1 AND user_id = $2`. 0행이면 `404`.
   - 부수 효과: 수정·삭제도 같은 WHERE 를 쓰므로 **거절될 때 상대방 자료가 한 글자도 바뀌지 않는다** (T07-C122).
3. **자식 자원**(`run_log`, `task_completion`)은 부모 `task` 를 소유 조건으로 먼저 조회하고, 없으면 `404`.
4. **거절 코드**: 로그인 안 됨 = `401`(API) / `/login` 리다이렉트(화면). 남의 자료 = `404`.
5. **화면에서 숨기는 것은 막은 것이 아니다.** 모든 차단은 서버 라우트의 SQL WHERE 절에서 일어난다.

## 6-A. 계층 구조 (MVC + DTO)

과제 요구사항은 아니지만, **"무엇이 어디서 막히는가"를 구조로 설명할 수 있게** 계층을 나눈다. 인증·인가는 여러 곳에 흩어지기 쉬운 관심사이고, 흩어지면 한 군데만 빠뜨려도 뚫린다. 계층을 고정하면 **소유자 조건이 어느 계층에 있는지**가 한 문장으로 답해진다.

### 6-A-1. 계층과 책임

```
app/**/page.tsx            View        화면. 서비스 결과를 받아 그리기만 한다
app/api/**/route.ts        Controller  요청 해석 → 세션 확인 → 서비스 호출 → DTO 로 응답
lib/service/*.ts           Service     업무 규칙과 트랜잭션 경계
lib/repository/*.ts        Repository  SQL. 소유자 조건이 여기에 있다
lib/domain/*.ts            Domain      순수 함수 (기간 계산, 집계 규칙, 검증 규칙)
lib/dto/*.ts               DTO         요청 입력 변환과 응답 화이트리스트
lib/db.ts, lib/http.ts     Infra       연결과 요청 유틸
```

### 6-A-2. 계층 규칙 (어기면 리뷰에서 되돌린다)

| 규칙 | 이유 |
|---|---|
| **Controller 에 SQL 을 쓰지 않는다** | SQL 이 흩어지면 소유자 조건을 빠뜨린 곳이 생긴다 |
| **Repository 는 쿠키·요청·응답을 모르게 한다** | HTTP 를 모르는 계층이라야 테스트에서 그대로 부를 수 있다 |
| **Repository 의 모든 조회·수정·삭제는 `user_id` 를 인자로 받는다** | 소유자 없이 부를 수 있는 함수를 아예 만들지 않는다. **빠뜨릴 자리를 없앤다** |
| **트랜잭션은 Service 에서만 연다** | 계정 삭제처럼 여러 표를 건드리는 일이 한 경계 안에서 끝난다 |
| **응답은 반드시 DTO 를 거친다. DB 행을 그대로 반환하지 않는다** | `SELECT *` 가 새 컬럼을 자동으로 실어 나르는 사고를 막는다 |
| **Domain 은 DB·HTTP 를 import 하지 않는다** | 집계·기간·검증 규칙을 `node --test` 로 바로 검사할 수 있다 |

### 6-A-3. 파일 배치

| 계층 | 파일 |
|---|---|
| Repository | `lib/repository/user.ts`, `session.ts`, `identity.ts`, `plan.ts`, `task.ts`, `run.ts`, `review.ts` |
| Service | `lib/service/auth.ts`(가입·로그인·중복확인·비밀번호 변경), `oauth.ts`(소셜 로그인·계정 연결), `plan.ts`, `task.ts`, `review.ts`, `account.ts`(내보내기·계정 삭제) |
| Domain | `lib/domain/rules.ts`(아이디·닉네임·비밀번호 규칙), `planner.ts`(기존), `query.ts`(기존 `buildTaskWhere`), `metric.ts`(오차율·결측·이상치·반올림) |
| DTO | `lib/dto/user.ts`, `plan.ts`, `task.ts`, `run.ts`, `review.ts` |

> 기존 `lib/planner.ts` 와 `lib/query.ts` 는 이미 순수 함수라 **`lib/domain/` 으로 옮기기만 한다.** 내용은 바꾸지 않는다.

### 6-A-4. 출력 DTO

| 함수 | 내보내는 필드 |
|---|---|
| `publicUser(row)` | `id`, `nickname` — **그 밖은 내보내지 않는다** |
| `me(row)` | 본인 계정 화면 전용. `id`, `login_id`, `nickname`, `email`, `created_at` — **`password_hash` 는 절대 포함하지 않는다** |
| `publicPlan` / `publicTask` / `publicRun` / `publicReview` | 화면과 내보내기에 필요한 필드만 화이트리스트로 명시 |

지금 `app/api/export/route.ts` 는 `SELECT *` 를 쓴다. 오늘은 새어 나갈 것이 없지만, `app_user`·`user_session` 이 생기고 `plan`/`task` 에 `user_id` 가 붙는 순간부터 **`SELECT *` 는 새 컬럼을 자동으로 응답에 실어 나른다.** 필드를 매번 골라 적는 방식은 언젠가 빠뜨리지만, 화이트리스트는 빠뜨릴 수가 없다 (T07-C105 / C106).

자동 검사에 `publicUser` 와 `me` 가 `password_hash` 를 **절대 포함하지 않는다**는 항목과, **Repository 의 조회 함수가 `user_id` 없이 호출되지 않는다**는 항목을 넣는다.

### 6-A-5. 이 구조가 포트폴리오에서 답해 주는 질문

| 질문 | 이 구조의 답 |
|---|---|
| 남의 자료는 어디서 막히나요 | Repository. 모든 함수가 `user_id` 를 인자로 받아 WHERE 에 넣습니다 |
| 화면에서 숨긴 것 아닌가요 | View 는 서비스 결과를 그리기만 합니다. 차단은 SQL 에서 일어납니다 |
| 비밀번호 해시가 샐 일은 없나요 | 응답은 DTO 화이트리스트만 통과합니다. 새 컬럼이 자동으로 끼어들 수 없습니다 |
| 규칙을 어떻게 검사했나요 | Domain 이 DB·HTTP 를 모르는 순수 함수라 그대로 단위 검사합니다 |

## 7. 세션 규칙 (T07-C108 ~ C115)

| 항목 | 값 |
|---|---|
| 사람을 알아보는 방법 | **서버 DB 에 저장한 세션**(불투명 난수 토큰). 비밀번호·구글·카카오 어느 쪽으로 들어와도 동일 |
| 쿠키 이름 | `pds_session` |
| 쿠키 속성 | `HttpOnly` · `Secure` · `SameSite=Lax` · `Path=/` |
| 토큰 원문 | `randomBytes(32)` 를 base64url 로 인코딩 (43자) |
| DB 저장 형태 | `sha256(원문)` 64자 hex. **원문은 서버에도 남기지 않는다** |
| 만료 | 발급 후 **7일**(절대 만료). 쿠키 `Max-Age` 와 DB `expires_at` 이 같은 값 |
| 로그아웃 | **DB 행 DELETE** + 쿠키 삭제 → 같은 쿠키 값을 다시 보내도 401 (T07-C109 / C114) |
| 비밀번호 변경 | 해당 사용자의 세션 **전부 DELETE** |
| URL 노출 | 세션 값은 쿠키로만 오간다 (T07-C112) |
| 제공자 토큰 | 구글·카카오의 액세스 토큰과 id_token 은 **저장하지 않는다.** 신원 확인 직후 버린다 |

### 7-1. 이제 지켜야 할 진짜 비밀값 (T07-C113 / C46)

소셜 로그인을 붙이면서 **실제 비밀키가 생겼다.** 전부 서버 전용 환경변수로만 둔다.

| 이름 | 용도 |
|---|---|
| `DATABASE_URL` | DB 접속 |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | 구글 OIDC |
| `KAKAO_CLIENT_ID` / `KAKAO_CLIENT_SECRET` | 카카오 OIDC |

- `NEXT_PUBLIC_` 접두어를 **절대 붙이지 않는다.** 붙이면 브라우저 번들에 들어간다.
- `.gitignore` 의 `.env*` 로 커밋을 막고, 제출 전에 빌드 산출물과 git 이력을 스캔한다.
- 세션 토큰은 여전히 서명하지 않으므로 **세션용 서명키는 존재하지 않는다.**

## 8. 가입 규칙과 계정 문구

### 8-1. 아이디·닉네임 규칙과 중복확인 (T07-C98)

일반 회원가입은 **아이디 · 닉네임 · 이메일 · 비밀번호** 네 칸을 받는다. 로그인은 **아이디 + 비밀번호**로 한다.

| 항목 | 규칙 |
|---|---|
| 아이디 (`login_id`) | 4~20자, 영문 소문자·숫자·밑줄(`_`)만. 첫 글자는 영문. **대소문자를 무시하고 중복 불가** |
| 닉네임 (`nickname`) | 2~20자, 앞뒤 공백 제거. **대소문자를 무시하고 중복 불가** |
| 이메일 (`email`) | 형식 검사 후 소문자로 정규화. **중복 불가** |

**중복확인은 두 겹으로 한다.**

1. **입력 중 확인(편의)** — 아이디·닉네임 칸에서 포커스가 빠지면 `POST /api/auth/check` 로 물어보고
   `사용 가능한 아이디입니다` / `이미 사용 중입니다` 를 그 자리에서 보여준다.
   - 이 응답은 **사용 가능 여부(true/false)만** 돌려준다. 다른 사람의 이메일이나 계정 정보를 절대 함께 돌려주지 않는다.
   - 검사 대상은 아이디와 닉네임뿐이다. **이메일은 이 경로로 확인해 주지 않는다** — 누가 가입했는지 캐낼 수 있기 때문이다.
2. **실제로 막는 것은 DB 유니크 인덱스** — `app_user_login_id_key`, `app_user_nickname_key`, `app_user_email_key`.
   화면에서 확인한 뒤 제출하기 전에 남이 먼저 가입해 버리는 경우까지 여기서 잡힌다. 위반은 `409` 로 응답한다.

> 화면 확인만 믿고 DB 제약을 빼면, 두 사람이 동시에 같은 아이디로 가입하는 순간 중복이 그대로 들어간다.
> **중복확인 버튼은 편의이고, 보장은 DB 가 한다.**

### 8-2. 비밀번호 규칙 (일반 회원가입 전용)

이메일+비밀번호로 가입하거나 비밀번호를 바꿀 때 **아래를 모두 만족해야 한다.**

| 조건 | 값 |
|---|---|
| 최소 길이 | **10자 이상** |
| 영문 대문자 | **1자 이상** (`A-Z`) |
| 영문 소문자 | **1자 이상** (`a-z`) |
| 숫자 | **1자 이상** (`0-9`) |
| 특수문자 | **1자 이상** (영문·숫자·공백이 아닌 문자) |
| 최대 길이 | 128자 (과도한 입력으로 해시 비용이 폭증하는 것을 막는다) |

- 검사는 **`lib/domain/rules.ts` 의 `checkPasswordRule()` 한 곳**에서만 한다. 가입·비밀번호 변경 두 경로가 이 함수를 지난다.
- **화면 검사는 편의일 뿐이고, 서버에서 반드시 다시 검사한다.** 브라우저를 거치지 않은 요청도 막아야 하기 때문이다.
- 위반 시 `400` 과 함께 **어떤 조건이 빠졌는지 알려준다.** 가입 단계에서는 계정 존재 여부가 새지 않으므로 구체적으로 안내해도 안전하다.
  예: `비밀번호는 10자 이상이며 대문자·소문자·숫자·특수문자를 각각 1자 이상 포함해야 합니다.`
- **소셜 전용 계정에는 이 규칙을 적용하지 않는다.** 비밀번호가 없기 때문이다. 소셜 계정이 나중에 비밀번호를 설정하면 그때 규칙이 적용된다.
- 자동 검사(`npm test`)에 규칙 검사를 넣는다: 조건별로 하나씩 빠진 값이 모두 거절되고, 모두 갖춘 값이 통과하는지 확인한다.

### 8-3. 계정 문구 규칙

- 로그인 실패 문구는 **아이디가 없을 때와 비밀번호만 틀렸을 때가 완전히 같다** (T07-C99):
  `아이디 또는 비밀번호가 올바르지 않습니다.` — 상태코드도 둘 다 `401`.
  계정이 없거나 소셜 전용 계정이어서 `password_hash` 가 비어 있을 때도 더미 해시로 비교를 한 번 돌려, 응답 시간 차이로 계정 존재 여부가 새지 않게 한다.
- **가입 단계와 로그인 단계의 문구 정책이 다르다.** 가입에서는 무엇이 중복인지 알려 줘도 되지만(어차피 중복확인 기능이 알려 준다), 로그인에서는 계정 존재 여부를 절대 알려 주지 않는다.
  - 가입 중복: `이미 사용 중인 아이디입니다.` / `이미 사용 중인 닉네임입니다.` / `이미 가입된 이메일입니다.` — 모두 `409`
- **비밀번호는 로그에 절대 남기지 않는다** (T07-C105 / C106). 규칙 위반 응답에도 입력한 값을 되돌려주지 않는다.

## 9. 5일 사용을 위한 집계 규칙 (T07-C04 ~ C15, C23 ~ C27)

`docs/5일_사용기록.md` 에 1일차 고정값으로 적고, 화면 집계도 같은 규칙을 쓴다.

| 규칙 | 값 |
|---|---|
| 시간 단위 | **분(minute)** |
| 날짜 기준 | **Asia/Seoul** |

## 11. 아직 못 막은 것 (T07-C130 초안)

구현 후 실제 상태로 확정한다. 현재 계획상 **하지 않기로 한 것**:

- **무차별 대입(brute force) 방어 없음** — 로그인 시도 횟수 제한·계정 잠금·CAPTCHA 가 없다. 비밀번호 복잡도 규칙(8-1)이 추측 난이도를 크게 올려 주지만, **시도 자체를 막지는 못한다.**
- **비밀번호 재설정 없음** — 잊으면 복구 수단이 없다.
- **두 번째 인증 수단(2FA) 없음**
- **보안 이벤트 로그 없음** — 침입이 일어나도 알아차릴 수 없다.
- **CSRF 토큰 없음** — `SameSite=Lax` 쿠키에만 의존한다.
- **유출된 비밀번호 목록 대조 없음** — 복잡도 조건은 갖췄지만 이미 유출된 흔한 비밀번호(`Password1!` 같은)는 그대로 통과한다.
- **같은 사람의 계정이 갈라질 수 있음** — 카카오가 이메일을 주지 않으면(비즈 앱 심사 전) 기존 계정에 연결하지 못하고 새 계정이 만들어진다. 계정 병합 기능은 만들지 않는다.
- **소셜 계정 연결 해제 없음** — 한 번 붙인 구글·카카오를 화면에서 끊을 수 없다.
- **중복확인 API 로 아이디·닉네임 존재 여부를 캐낼 수 있다** — `/api/auth/check` 는 사용 가능 여부만 돌려주지만, 반복 호출하면 "어떤 아이디가 이미 있는지" 목록을 만들 수 있다. 호출 횟수 제한을 두지 않았다. 이메일은 이 경로에서 확인해 주지 않아 피해 범위를 줄였다.
- **PR 병합 전까지 과제 6 주소에서 자료가 공개된다** — DB 를 함께 쓰기 때문이다 (0-1 참조).
