# 과제 6 — 플랜두씨 다이어리 실행 계획 (v1)

작성일 2026-08-31 · 작성자 Claude Code(Architect/Planner) · 근거: 사용자가 제공한 과제 6 원문만 사용
계획 시간 8~10h · 로그인 없음 · 서버 데이터베이스 필수

---

## 1. 과제 한 줄 정의

계획(Plan) → 실제로 한 일(Do) → 돌아보기(See)가 **하나의 서버 데이터베이스로 이어지고**,
돌아보기의 집계 숫자를 눌러 **근거 기록까지 되짚어 갈 수 있으며**,
거기서 얻은 고칠 점 한 줄이 **다음 계획으로 되돌아가는** 다이어리를 만든다.

제출물 4종: ① 결과물 주소 ② 소스 주소 ③ 짧은 확인 방법 4줄 ④ AI와 내 판단 3줄

## 2. 기술 선택과 근거

| 항목 | 선택 | 근거 |
|---|---|---|
| 앱 | Next.js(App Router) 단일 프로젝트 | 화면과 서버 API가 한 저장소·한 배포. 프론트/백 분리 시 배포처 2곳, CORS, 환경변수 2벌이 생겨 8~10h 예산에 불리 |
| DB | 관리형 Postgres (Neon / Supabase 등 무료 티어) | C34 "서버의 실제 데이터베이스" 충족. 접속 문자열은 **서버 라우트에서만** 사용 |
| DB 접근 | 원시 SQL + `schema.sql` 한 장 | ORM/마이그레이션 도구는 이 규모에 과함. 표 6개짜리 스키마에 도구를 얹지 않는다 |
| 배포 | Vercel(앱) + 관리형 DB | 무료, GitHub 푸시 후 자동 배포, 시크릿 창 접속 가능(C01) |
| 스타일 | 기본 CSS 또는 이미 익숙한 도구 | 채점 항목 아님. 시간 쓰지 않는다 |

**금지 사항 (C58 직결)**: DB 접속 문자열·서비스 키를 클라이언트 컴포넌트, `NEXT_PUBLIC_*`,
저장소, 커밋 이력 어디에도 넣지 않는다. 브라우저는 오직 `/api/*` 만 호출한다.

## 3. 데이터 모델

### 3.1 표 구조

```
plan            계획 본체
  id, title, start_date, end_date, priority, success_criteria,
  estimate_minutes, carried_from_review_id(NULL 가능), created_at, updated_at

plan_revision   계획 수정 이력 (C08)
  id, plan_id, title, start_date, end_date, priority, success_criteria,
  estimate_minutes, revised_at        ← 수정 "직전" 값을 그대로 보관

task            할 일
  id, plan_id, title, note, due_date, priority, tags(text[]),
  estimate_minutes, created_at, updated_at, deleted_at(NULL=살아있음)

task_completion 완료 상태 (C21/C22)
  task_id PRIMARY KEY, completed_at
  ← 할 일 하나당 최대 한 행. 완료=INSERT ON CONFLICT DO NOTHING, 되돌리기=DELETE

run_log         실제로 한 일 (C23~C27)
  id, task_id, started_at, ended_at, actual_minutes, blocker_reason, created_at

review          돌아보기 + 다음 계획으로 넘길 한 줄 (C33)
  id, period_start, period_end, next_action, created_at
```

### 3.2 확정 규칙 (구현 전에 못 박고 시작)

1. **시간 단위는 전부 분(minute)** — 저장·계산·표시 모두 분. 화면에 "예상 90분 / 실제 120분 / 차이 +30분"처럼 단위를 붙여 쓴다. (C32, C35)
2. **날짜와 시각을 구분해서 저장**
   - `*_date`(마감일, 계획 기간): `date` 타입, **서울 날짜**로 저장. 시간대 변환 없음.
   - `*_at`(시작 시각, 끝난 시각): `timestamptz`, UTC 저장 → 화면에서 `Asia/Seoul`로 표시.
   - "오늘"은 항상 `(now() AT TIME ZONE 'Asia/Seoul')::date` 로 구한다. (C30)
3. **지우기는 소프트 삭제** — `task.deleted_at`. 집계는 전부 `deleted_at IS NULL` 조건. (C13, C28)
4. **계획 값과 실행 값은 표가 다르다** — 실행 기록 저장은 `run_log` INSERT만 한다. `plan`/`task`의 예상 시간은 어떤 경우에도 실행 기록이 덮어쓰지 않는다. (C27)
5. **계획 수정 이력은 DB 트리거로** — `BEFORE UPDATE ON plan` 트리거가 OLD 행을 `plan_revision`에 넣는다. 애플리케이션 코드에서 깜빡할 여지를 없앤다. (C08)
6. **완료 중복은 DB 제약으로** — `task_completion.task_id`가 기본키. 버튼 비활성화에 기대지 않는다. 연타해도 두 번째 INSERT는 무시된다. (C21/C22)

### 3.3 `contracts/pds-schema-v2.json`

위 표·항목·관계와 날짜 규칙(3.2 전체)을 JSON으로 기록해 최종 소스에 포함한다. 담을 항목:
`tables[]`(컬럼·타입·NULL 허용), `relations[]`(외래키), `date_rules`(저장 시간대/표시 시간대/오늘 정의),
`unit_rules`(분 고정), `soft_delete`, `aggregate_definitions`(4.2의 다섯 식 그대로). (카드 5 요구)

## 4. 핵심 규칙 명세

### 4.1 정렬·검색·거르기 (C18~C20)

- **정렬 기준을 화면에 문장으로 적어 둔다**: "마감일 빠른 순 → 우선순위 높은 순 → 등록 번호 순"
- SQL: `ORDER BY due_date ASC NULLS LAST, priority DESC, id ASC`
  마지막 `id ASC`가 동점 처리자다. 이게 없으면 볼 때마다 순서가 흔들린다.
- 검색: 제목·메모 부분 일치(대소문자 무시). 거르기: 상태 / 우선순위 / 태그 / 지연만.
- 검색·거르기·정렬은 **전부 서버 SQL에서** 처리한다. 화면에서 한 번 더 섞지 않는다.

### 4.2 돌아보기 집계 정의 (C28~C32) — 이 다섯 줄이 채점의 핵심

대상 집합 T = `deleted_at IS NULL` 이고 `due_date`가 조회 기간 안에 드는 할 일.

| 지표 | 정의 |
|---|---|
| 계획 수 | `COUNT(T)` |
| 완료 수 | `COUNT(T 중 task_completion 이 있는 것)` |
| 지연 수 | `COUNT(T 중 완료 없음 AND due_date < 서울 오늘)` — 완료된 건은 절대 세지 않음 |
| 막힘 수 | `COUNT(DISTINCT task_id)` — `run_log.blocker_reason`이 비어 있지 않은 기록을 가진 T의 할 일 |
| 예상/실제/차이 | 예상 `SUM(T.estimate_minutes)`, 실제 `SUM(T에 붙은 run_log.actual_minutes)`, 차이 `실제 − 예상`. 대상이 없으면 셋 다 `0`(NULL 금지) |

### 4.3 숫자 → 근거 기록 되짚기 (C83)

각 집계 숫자는 링크다. `/tasks?from=..&to=..&metric=overdue` 형태로 이동하고,
도착한 목록 화면 맨 위에 **"2026-08-01~08-31 기간의 지연 5건"** 처럼 조건을 글로 다시 적어 준다.
목록 건수와 집계 숫자가 어긋나지 않도록 **조건 생성 함수를 한 개만 두고 집계와 목록이 함께 쓴다.**
(두 곳에 따로 쓰면 숫자와 목록이 어긋난다 — 이 과제에서 가장 흔한 실패 지점)

### 4.4 다음 계획으로 이월 (C33)

돌아보기 화면 → `review.next_action`에 고칠 점 한 줄 저장 → **"이 한 줄로 계획 만들기"** 버튼 →
계획 등록 폼이 그 문장으로 미리 채워지고 `plan.carried_from_review_id`가 기록됨 →
계획 상세에 "이 계획은 (기간) 돌아보기에서 넘어왔습니다" 표시. 화면에서 되돌아온 게 보여야 통과다.

## 8. 검증

**자동 검사 1벌** (`test/*.test.js`, 프레임워크 없이 `node --test` + assert, 현재 9건):

1. 집계 다섯 식이 준비된 표본 자료에서 기대값과 일치 (C28~C32)
2. 완료 API 두 번 호출 → `task_completion` 1행, 완료 수 +1 (C21/C22)
3. 계획 수정 후 `plan_revision`에 이전 값 존재 (C08)
4. 실행 기록 저장 전후 `task.estimate_minutes` 불변 (C27)
5. 같은 정렬 조건으로 2회 조회 시 순서 동일 (C20)
6. 일간·주간·월간 날짜 범위와 날짜 이동 규칙 일치

**손으로 하는 확인** (제출용 4줄과 동일하게):

- 어디로 가나요: 배포 주소 `/` 접속
- 세 단계 안에 무엇을 하나요: ① 할 일의 완료 버튼 연타 ② `/review` 이동 ③ 완료 수 숫자 클릭
- 무엇이 보이면 통과인가요: 완료 수가 1만 늘고, 숫자를 누르면 그 완료 건 목록이 조건 문장과 함께 보임
- 안 될 때는 무엇이 보이나요: 오류 띠에 "저장하지 못했습니다 — 다시 시도" 문구 (빈 화면·무반응 금지)

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|

| 공개 상태에서 민감한 내용 노출 | 남이 봐도 되는 범위만 입력. 타인 이름·연락처 금지. 잠금은 과제 7 |
