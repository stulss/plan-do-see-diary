## ① 무엇으로 붙였나 (T07-C91 / C92 / C101 / C107 / C108)

| 구분 | 선택 | 이름 / 버전 |
|---|---|---|
| 인증 방식 | **직접 구현(자체 세션)** + 검증된 라이브러리 조합 | — |
| 로그인 방법 | **아이디+비밀번호 · 구글 · 카카오** 세 가지 | — |
| 비밀번호 되돌릴 수 없게 만들기 | **bcrypt** | `bcryptjs` `(설치 버전 기입)` — 작업 계수 12 |
| 소셜 로그인 | **OpenID Connect** | `openid-client` `(설치 버전 기입)` — PKCE·state·id_token 서명 검증 내장 |
| 소셜 제공자 | 구글 / 카카오 | `accounts.google.com` / `kauth.kakao.com` |
| 세션 토큰 생성·해시 | Node 표준 라이브러리 `node:crypto` | `randomBytes(32)`, `createHash("sha256")` |
| 사람을 알아보는 방법 | **서버 DB 에 저장한 세션** (JWT 아님) | `user_session` 표 + `pds_session` 쿠키 |
| 프레임워크 | Next.js | `16.3.3` (App Router) |
| DB | PostgreSQL | `(관리형 서비스·버전 기입)` — **과제 6과 같은 DB 를 공유** |

**비밀번호 처리는 `bcryptjs` 에, 소셜 로그인의 OAuth/OIDC 흐름은 `openid-client` 에 맡겼다** (T07-C107).
**직접 만든 부분은 세션 관리(발급·조회·폐기)와 계정 연결 규칙**이며, 그 사실을 여기에 그대로 적는다. 세션 토큰 자체는 표준 라이브러리의 난수 생성기(`randomBytes`)가 만든다.

**구글·카카오로 들어와도 로그인 상태를 유지하는 것은 우리 세션이다.** 제공자의 액세스 토큰과 `id_token` 은 신원을 한 번 확인하는 데만 쓰고 저장하지 않는다. 그래서 소셜 로그인이어도 **로그아웃 즉시 무효화(T07-C114)** 가 똑같이 성립한다.

## ② 왜 그걸 골랐나 (T07-C93 / C102)

### 인증 방식 — 직접 구현(자체 세션)을 고른 이유

통과 기준 **T07-C114** 는 *"로그아웃하면 이전에 발급한 값이 더는 통하지 않는다"* 를 요구한다.
이 한 줄이 선택을 결정했다. **서버가 세션을 폐기할 수 있어야** 하기 때문이다.

| 함께 검토했지만 고르지 않은 방법 | 고르지 않은 이유 (한 문장) |
|---|---|
| **Auth.js (NextAuth) v5** | 소셜만 쓰면 DB 세션이 가능하지만 **Credentials(비밀번호) Provider 를 함께 쓰는 순간 세션 전략이 JWT 로 고정**되어, 로그아웃해도 이미 발급된 토큰이 만료 전까지 유효하므로 T07-C114 를 만족시킬 수 없다. |
| **Supabase Auth (인증 서비스)** | 로그아웃 뒤에도 액세스 토큰이 만료 전까지 유효해 "같은 값으로 다시 요청 → 거절" 장면을 만들 수 없고, 과제 6의 원시 SQL 데이터 접근 계층을 RLS 기반으로 전부 새로 써야 한다. |
| **arctic (소셜 로그인 전용 클라이언트)** | 자체 세션과 조합하기 좋은 후보였으나 **2026년 7월 지원이 중단**되어 새로 도입하지 않았다. |
| **OAuth 흐름 직접 구현 (raw fetch)** | state·PKCE·`id_token` 서명 검증을 직접 짜야 해서, 보안 경로에 자체 코드가 늘어난다. |
| **express-session 계열 세션 미들웨어** | Next.js App Router 는 Express 미들웨어 스택을 쓰지 않아, 어댑터를 얹는 비용이 세션 표 하나 만드는 비용보다 크다. |

> 남이 만든 것을 쓰는 것은 감점이 아니다. 다만 **이번 요구사항에서는 널리 쓰이는 인증 라이브러리가 요구를 못 맞춘다**는 것이 확인되어 세션만 직접 만들었고, 위험이 큰 비밀번호 처리와 OIDC 흐름은 라이브러리에 맡겼다.

### 왜 소셜 로그인만 쓰지 않았나

카드 2(T07-C101 ~ C107)는 **저장된 비밀번호의 모습**과 **같은 비밀번호로 만든 두 계정의 저장값이 다름**을 증거로 요구한다.
소셜 로그인만 쓰면 비밀번호가 아예 없어 이 증거를 만들 수 없다. 그래서 아이디+비밀번호 로그인을 **유지**하고 소셜을 추가했다.

### 해시 방법 — bcrypt 를 고른 이유 (T07-C102)

**bcrypt 는 계정마다 무작위 소금값(salt)을 스스로 만들어 해시 문자열 안에 함께 담기 때문에, 같은 비밀번호로 만든 두 계정의 저장값이 반드시 서로 달라지고 소금값을 직접 관리하는 코드를 쓰지 않아도 된다.**

| 검토한 다른 해시 방법 | 고르지 않은 이유 |
|---|---|
| `node:crypto` 의 scrypt | 소금값 생성·저장 형식·상수시간 비교를 직접 작성해야 해서, 비밀번호 경로에 직접 만든 코드가 늘어난다. |
| PBKDF2 | 같은 이유에 더해, 같은 비용에서 GPU 병렬 공격 저항이 bcrypt 보다 약하다. |
| argon2 | 가장 권장되지만 네이티브 빌드가 필요해 서버리스 배포에서 실패 위험이 있다. |
| SHA-256 1회 | 소금값이 없고 너무 빨라 사전 공격에 무력하다. |

### 구조 — MVC 계층 + DTO

인증과 인가는 흩어지기 쉬운 관심사다. 라우트마다 소유자 조건을 적는 방식은 **새 엔드포인트가 하나 늘 때마다 빠뜨릴 기회를 만든다.**
그래서 계층을 고정하고 **"소유자 조건은 Repository 에만 있다"** 를 규칙으로 삼았다.

```
app/**/page.tsx        View        화면. 서비스 결과를 그리기만 한다
app/api/**/route.ts    Controller  요청 해석 → 세션 확인 → 서비스 호출 → DTO 응답 (SQL 금지)
lib/service/           Service     업무 규칙과 트랜잭션 경계
lib/repository/        Repository  SQL. 모든 함수가 user_id 를 인자로 받는다
lib/domain/            Domain      순수 함수 (planner, query, rules, metric)
lib/dto/               DTO         응답 필드 화이트리스트
```

| 계층 규칙 | 이유 |
|---|---|
| Controller 에 SQL 을 쓰지 않는다 | SQL 이 흩어지면 소유자 조건을 빠뜨린 곳이 생긴다 |
| **Repository 의 모든 조회·수정·삭제는 `user_id` 를 인자로 받는다** | 소유자 없이 부를 수 있는 함수를 아예 만들지 않는다. **빠뜨릴 자리를 없앤다** |
| 트랜잭션은 Service 에서만 연다 | 계정 삭제처럼 여러 표를 건드리는 일이 한 경계 안에서 끝난다 |
| 응답은 반드시 DTO 를 거친다 | `SELECT *` 가 새 컬럼(`password_hash`, `token_hash`)을 자동으로 응답에 실어 나르는 사고를 막는다 (T07-C105 / C106) |
| Domain 은 DB·HTTP 를 import 하지 않는다 | 규칙을 `node --test` 로 바로 검사할 수 있다 |

비용은 파일 수가 늘어난다는 것이고, 얻는 것은 **"남의 자료가 어디서 막히나요"에 계층 한 줄로 답할 수 있다**는 것이다.

### 사용자 ID 를 얻는 유일한 경로 (T07-C123)

```
요청  →  쿠키 pds_session  →  sha256  →  user_session.token_hash 조회  →  user_id
```

**URL 경로·쿼리스트링·요청 헤더·요청 본문에서 사용자 ID 를 읽는 코드는 존재하지 않는다.**

```
(붙이기: app/ lib/ 검색 결과 — 요청에서 사용자 ID 를 읽는 코드 0건)
```

| 항목 | 규칙 | 막는 곳 |

| 닉네임 | 2~20자. 대소문자 무시 중복 불가 | `app_user_nickname_key` 유니크 인덱스 |
| 이메일 | 형식 검사 후 소문자 정규화. 중복 불가 | `app_user_email_key` 유니크 인덱스 |
| 비밀번호 | **10자 이상 + 대문자·소문자·숫자·특수문자 각 1자 이상** | `lib/service/auth.ts` 의 `checkPasswordRule()` (서버에서 재검사) |

**중복확인은 두 겹이다.** 입력 중 `/api/auth/check` 가 사용 가능 여부를 알려 주지만, **실제로 막는 것은 DB 유니크 인덱스**다. 화면에서 확인한 뒤 제출하기 전에 남이 먼저 가입하는 경우까지 여기서 잡힌다.
`/api/auth/check` 는 **아이디와 닉네임만** 확인해 준다. 이메일까지 열어 주면 누가 가입했는지 캐낼 수 있기 때문이다.

## ④ 안 열리는 것을 확인한 기록 (T07-C129)

확인 다섯 가지를 **성공한 요청 / 거절된 요청** 짝으로 적는다. 두 요청은 **같은 주소·같은 방식**이고 달라진 것은 한 가지뿐이어야 한다.

> 아래 `(붙이기)` 자리에 실제 요청·응답을 그대로 옮긴다. 비밀값은 가린다.

### 검사용 계정

| 계정 | 아이디 | 용도 | 넣어 둔 자료 |
|---|---|---|---|
| 내 계정 | `owner` | 과제 6 자료를 옮긴 계정 | 계획 `(n)`건 · 할 일 `(n)`건 · 실행 기록 `(n)`건 |
| 남의 계정 | `other` | 차단 확인용 | 계획 `(n)`건 · 할 일 `(n)`건 |

**두 계정의 비밀번호는 이 문서에 적지 않는다** (T07-C116).

### 확인 1. 로그인하지 않으면 자료가 안 열린다 (T07-C97 / C124)

**거절**
```http
GET /api/tasks HTTP/1.1
(쿠키 없음)

→ (붙이기)
```

**성공** — 같은 주소·같은 방식에 로그인 쿠키만 추가

### 확인 3. 로그아웃 뒤 같은 값으로 다시 요청하면 거절된다 (T07-C109 ~ C111 / C114)

**성공 — 로그인 상태**
```http
GET /api/tasks HTTP/1.1
Cookie: pds_session=Ab3xK9…생략

→ (붙이기: 200 + 내 자료)
```

**로그아웃**
```http
POST /api/auth/logout HTTP/1.1
Cookie: pds_session=Ab3xK9…생략

→ (붙이기)
```

**거절 — 같은 주소·같은 방식·같은 쿠키 값**
```http
GET /api/tasks HTTP/1.1
Cookie: pds_session=Ab3xK9…생략      ← 위와 완전히 같은 값

→ (붙이기: 401)
```

> 달라진 것은 **로그아웃 여부 하나뿐**이다 (T07-C110).
> 서버가 `user_session` 행을 지웠기 때문에 브라우저에 값이 남아 있어도 통하지 않는다.

**소셜 로그인도 마찬가지**: 구글/카카오로 로그인한 세션도 같은 방식으로 끊긴다.
```
(붙이기: 소셜 로그인 → 성공 200 → 로그아웃 → 같은 쿠키로 401)
```

**만료** (T07-C111): 세션은 발급 후 **7일** 뒤 끊긴다. 쿠키 `Max-Age` 와 DB `expires_at` 이 같은 값이다.
`expires_at` 을 과거로 바꾼 뒤 같은 요청:
```
(붙이기: 401)
```

**비밀번호 변경 시 이전 세션 무효** (T07-C114):
```
(붙이기: 변경 전 쿠키로 요청 → 401)
```

**세션 값이 주소창에 실리지 않음** (T07-C112):
```
(붙이기: 토큰을 쿼리스트링으로 넘기는 코드 0건)
```

**비밀키** (T07-C113): 세션 토큰은 서명하지 않으므로 **세션용 서명키는 존재하지 않는다.**
소셜 로그인 때문에 생긴 **클라이언트 시크릿**(`GOOGLE_CLIENT_SECRET`, `KAKAO_CLIENT_SECRET`)과 DB 접속 문자열은 서버 전용 환경변수에만 둔다.
```
(붙이기: .next 빌드 산출물 스캔 0건 / git log -p 스캔 0건 / .env* 가 .gitignore 에 있음 / NEXT_PUBLIC_ 접두어 사용 0건)
```

### 확인 4. 남의 자료가 읽기·수정·삭제 모두 거절된다 (T07-C117 ~ C122)

`owner` 로 로그인한 상태에서 `other` 의 자료(`task id = (n)`)를 건드린다.

| 방향 | 동작 | 요청 | 응답 |
|---|---|---|---|
| owner → other | 읽기 | `GET /api/tasks/(n)` | `(붙이기)` |
| owner → other | 수정 | `PATCH /api/tasks/(n)` | `(붙이기)` |
| owner → other | 삭제 | `DELETE /api/tasks/(n)` | `(붙이기)` |
| other → owner | 읽기 | `GET /api/tasks/(m)` | `(붙이기)` |
| other → owner | 수정 | `PATCH /api/tasks/(m)` | `(붙이기)` |
| other → owner | 삭제 | `DELETE /api/tasks/(m)` | `(붙이기)` |

**거절 방식** (T07-C121): `404` — 존재 자체를 감춘다. `WHERE id = $1 AND user_id = $2` 가 0행을 돌려주기 때문이다.

**거절 앞뒤로 반대편 자료가 그대로인지** (T07-C122)
```
거절 전  other 계정 자료 건수: 계획 (n) / 할 일 (n) / 실행 기록 (n)
거절 후  other 계정 자료 건수: 계획 (n) / 할 일 (n) / 실행 기록 (n)   ← 같음, 새로 생긴 자료 없음
(붙이기: 실제 COUNT 결과)
```

**주소·헤더·본문에 남의 계정을 적어 보내기** (T07-C123)
```http
GET /api/tasks?user_id=(other 의 id) HTTP/1.1
X-User-Id: (other 의 id)
Cookie: pds_session=(owner 의 값)…생략

→ (붙이기: 그래도 owner 자료만 돌아옴)
```

**목록에 남의 자료가 섞이지 않는다** (T07-C125)
```
(붙이기: GET /api/tasks 응답 전체. other 의 id 가 하나도 없음)
```

**이 거절을 만들어 내는 소스 위치** (T07-C126)
- `lib/session.ts` 의 `requireUser()` — 사용자 확정
- `lib/domain/query.ts` 의 `buildTaskWhere()` — 목록·집계의 소유 조건
- `app/api/tasks/[id]/route.ts` 의 `WHERE id = $1 AND user_id = $2` — 한 건 조회·수정·삭제

## ⑥ 아직 못 막은 것 (T07-C130)

> **이 항목을 비워 두지 않는다.** "다 막았다" 고 적는 것보다 못 막은 것을 정확히 적는 쪽이 좋은 제출물이다.

| 못 막은 것 | 왜 위험한가 |
|---|---|
| **무차별 대입(brute force)** | 로그인 시도 횟수 제한·계정 잠금·CAPTCHA 가 없다. 비밀번호 규칙(10자 + 대문자·소문자·숫자·특수문자)이 추측 난이도를 크게 올리고 bcrypt 작업 계수 12가 시도 1회당 시간을 늘려 주지만, **속도를 늦출 뿐 시도 자체를 막지는 못한다.** |
| **유출된 비밀번호 목록 대조 없음** | 복잡도 조건은 갖췄지만 이미 유출된 흔한 비밀번호(`Password1!` 같은)는 그대로 통과한다. |
| **비밀번호 재설정 수단 없음** | 비밀번호를 잊으면 계정과 그 안의 모든 기록에 접근할 수 없다. 소셜을 연결해 두지 않았다면 복구할 방법이 없다. |
| **두 번째 인증 수단(2FA) 없음** | 비밀번호 하나만 새면 계정이 그대로 넘어간다. |
| **보안 이벤트 로그 없음** | 로그인 실패가 몇 번 있었는지, 누가 언제 들어왔는지 기록이 없다. **침입이 일어나도 알아차릴 수 없고 사후 추적도 불가능하다.** |
| **CSRF 토큰 없음** | `SameSite=Lax` 쿠키에만 의존한다. 최신 브라우저에서는 대체로 막히지만 명시적 토큰보다 약하다. |
| **중복확인 API 로 아이디·닉네임을 캐낼 수 있음** | `/api/auth/check` 는 사용 가능 여부만 돌려주지만, 반복 호출하면 "어떤 아이디가 이미 있는지" 목록을 만들 수 있다. 호출 횟수 제한을 두지 않았다. 이메일은 이 경로에서 확인해 주지 않아 피해 범위를 줄였다. |
| **같은 사람의 계정이 갈라질 수 있음** | 카카오가 이메일을 주지 않으면(비즈 앱 심사 전) 기존 계정에 연결하지 못하고 새 계정이 만들어진다. 계정 병합 기능은 만들지 않았다. |
| **소셜 계정 연결 해제 없음** | 한 번 붙인 구글·카카오를 화면에서 끊을 수 없다. |
| **PR 병합 전까지 과제 6 주소에서 자료가 공개된다** | 과제 6과 DB 를 함께 쓰기 때문이다. 과제 6 배포는 인증이 없어, 병합 전에는 같은 자료가 로그인 없이 보인다. |
| `(구현 중 확인된 항목 추가)` | `(기입)` |
