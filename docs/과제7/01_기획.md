# 01. 기획 — 과제 7 「잠긴 플랜두씨 다이어리」 인증 설계

> 이 문서는 **과제 7**의 설계 기준이다. 구현은 이 문서를 따른다.
> 과제 6 설계는 `docs/01_기획.md` 에 그대로 남아 있다. **지우지 않는다.**

## 0. 전제

- 과제 6은 **최종 승인이 통과**되었다. 같은 저장소 `main` 브랜치에서 이어서 진행한다.
- **데이터베이스는 과제 6 것을 그대로 쓴다.** 자료가 갈라지면 안 되기 때문이다.
- 과제 6 문서·보고서·증거는 **그대로 유지**한다. 과제 7 산출물은 `docs/과제7/` 와 `과제7_작업내역_체크리스트.md` 에 모아 구분한다.
- 이어받은 과제 6 고정 commit: `356a46034e94084caec3e17eaaf2ab8d98cef7ce` (T07-C78 — `main` 이력에 조상으로 포함)

### 0-1. 같은 DB 를 쓰기 때문에 생기는 문제와 대응

과제 6 배포는 인증이 없어서 `plan`/`task`/`review` 에 `user_id` 없이 INSERT 한다.
`user_id` 를 처음부터 `NOT NULL` 로 잡으면 **인증판을 배포하기 전까지 과제 6 앱의 등록 기능이 깨진다.**

→ 소유자 컬럼에 **임시 `DEFAULT`** 를 걸어 소유자 계정으로 자동 귀속되게 하고, 인증판 배포 후 `DROP DEFAULT` 한다 (3-2 참조).

> 인증판을 배포하기 전까지는 과제 7에서 만든 자료가 과제 6 주소에서 로그인 없이 보인다.
> **배포·검증 직후 미루지 말고 인증판으로 전환**한다.

## 1. 무엇으로 붙이는가 (T07-C91 / C92)

이번 범위의 로그인 방법은 **아이디 + 비밀번호 하나**다.

| 구분 | 선택 | 이름 / 버전 |
|---|---|---|
| 전체 방식 | **직접 구현(자체 세션)** + 검증된 라이브러리 조합 | — |
| 비밀번호 해시 | 라이브러리 위임 | **bcryptjs** (설치 버전 고정) — 작업 계수 12 |
| 세션 토큰 | Node 표준 라이브러리 | `node:crypto` 의 `randomBytes(32)` / `createHash("sha256")` |
| 세션 보관 | 서버 DB `user_session` 표 | — |
| 세션 전달 | `HttpOnly; Secure; SameSite=Lax; Path=/` 쿠키 | — |

**핵심 성질**: 서명 기반 토큰(JWT)을 쓰지 않는다. 쿠키에 담기는 값은 **의미 없는 난수(opaque token)** 이고, 서버 DB 에 그 값의 SHA-256 해시가 남아 있어야만 유효하다.

## 2. 왜 그것을 골랐는가 (T07-C93 / C102)

### 2-1. 함께 검토했지만 고르지 않은 방법

통과 기준 **T07-C114** 는 *"로그아웃하면 이전에 발급한 값이 더는 통하지 않는다"* 를 요구한다.
이 한 줄이 선택을 결정했다. **서버가 세션을 폐기할 수 있어야** 하기 때문이다.

| 검토한 방법 | 고르지 않은 이유 |
|---|---|
| **Auth.js(NextAuth) v5 + Credentials Provider** | Credentials Provider 는 **세션 전략이 JWT 로 고정**되어 DB 세션을 쓸 수 없다. JWT 는 서버에 상태가 없어 로그아웃해도 이미 발급된 토큰이 만료 전까지 유효하므로 **T07-C114** 를 만족시킬 수 없다 |
| **Supabase Auth (인증 서비스)** | 로그아웃 뒤에도 액세스 토큰이 만료 전까지 유효해 "같은 값으로 다시 요청 → 거절" 장면을 만들 수 없다. 과제 6의 원시 SQL 접근 계층을 RLS 로 전부 새로 써야 하는 비용도 크다 |
| **express-session 계열 세션 미들웨어** | Next.js App Router 는 Express 미들웨어 스택을 쓰지 않아, 어댑터를 얹는 비용이 세션 표 하나 만드는 비용보다 크다 |

> 남이 만든 것을 쓰는 것은 감점이 아니다. 다만 **이번 요구사항에서는 널리 쓰이는 인증 라이브러리가 요구를 못 맞춘다**는 것이 확인되어 세션만 직접 만들었고, 위험이 큰 비밀번호 처리는 라이브러리에 맡겼다.

### 2-2. 해시 방법으로 bcrypt 를 고른 이유 (T07-C102)

bcrypt 는 **계정마다 무작위 소금값(salt)을 자동으로 만들어 해시 문자열 안에 함께 담기 때문에**, 같은 비밀번호로 만든 두 계정의 저장값이 반드시 서로 달라지고(T07-C104) 소금값 관리 코드를 직접 쓸 필요가 없다. `bcryptjs` 는 순수 자바스크립트라 서버리스에서 네이티브 빌드가 필요 없다.

| 검토한 다른 해시 방법 | 고르지 않은 이유 |
|---|---|
| `node:crypto` 의 scrypt | 소금값 생성·저장 형식·상수시간 비교를 직접 작성해야 한다 |
| PBKDF2 | 같은 이유에 더해, 같은 비용에서 GPU 병렬 공격 저항이 bcrypt 보다 약하다 |
| argon2 | 가장 권장되지만 네이티브 빌드가 필요해 서버리스 배포 실패 위험이 있다 |
| SHA-256 1회 | 소금값이 없고 너무 빨라 사전 공격에 무력하다 |

## 3. 데이터 모델 변경

### 3-1. 새로 만드는 표 (`schema_auth.sql`)

```sql
-- 계정. 로그인은 login_id 로 하고, 화면 표시는 nickname 으로 한다.
-- 이메일은 나중에 비밀번호 찾기에 쓰려고 함께 받는다.
CREATE TABLE app_user (
  id            bigserial PRIMARY KEY,
  login_id      text NOT NULL CHECK (btrim(login_id) <> ''),
  nickname      text NOT NULL CHECK (btrim(nickname) <> ''),
  email         text NOT NULL CHECK (btrim(email) <> ''),
  password_hash text NOT NULL,          -- bcrypt 해시. 원문은 어디에도 저장하지 않는다.
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
-- 아이디·닉네임·이메일은 대소문자를 무시하고 중복될 수 없다 (T07-C98).
-- 화면의 중복확인은 편의일 뿐이고, 실제로 막는 것은 이 세 인덱스다.
CREATE UNIQUE INDEX app_user_login_id_key ON app_user (lower(login_id));
CREATE UNIQUE INDEX app_user_nickname_key ON app_user (lower(nickname));
CREATE UNIQUE INDEX app_user_email_key    ON app_user (lower(email));

-- 세션. 쿠키에는 난수 원문이, 이 표에는 그 값의 SHA-256 해시만 들어간다.
-- DB가 통째로 유출돼도 저장된 값만으로는 남의 세션을 흉내 낼 수 없다.
CREATE TABLE user_session (
  token_hash text   PRIMARY KEY,        -- sha256(쿠키 원문) 64자 hex
  user_id    bigint NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
  expires_at timestamptz NOT NULL,      -- 발급 시각 + 7일 (T07-C111)
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX user_session_user_idx ON user_session (user_id);
```


### 3-2. 기존 표에 소유자 붙이기 (과제 6 DB 를 그대로 쓰면서)

**순서를 지켜야 과제 6 배포가 깨지지 않는다.**

```sql
-- 1) 먼저 NULL 허용으로 추가한다. 이 시점에도 과제 6 앱은 그대로 동작한다.
ALTER TABLE plan   ADD COLUMN user_id bigint REFERENCES app_user(id) ON DELETE CASCADE;
ALTER TABLE task   ADD COLUMN user_id bigint REFERENCES app_user(id) ON DELETE CASCADE;
ALTER TABLE review ADD COLUMN user_id bigint REFERENCES app_user(id) ON DELETE CASCADE;

-- 2) 소유자 계정을 화면에서 가입한 뒤, 과제 6에서 만든 기존 자료를 그 계정으로 옮긴다 (T07-C100).
UPDATE plan   SET user_id = :owner_id WHERE user_id IS NULL;
UPDATE task   SET user_id = :owner_id WHERE user_id IS NULL;
UPDATE review SET user_id = :owner_id WHERE user_id IS NULL;

-- 3) 임시 호환 장치.
--    인증판을 배포하기 전까지 과제 6 앱이 user_id 없이 INSERT 해도 소유자에게 귀속되게 한다.
--    인증판 배포 후 반드시 DROP DEFAULT 한다.
ALTER TABLE plan   ALTER COLUMN user_id SET DEFAULT :owner_id;
ALTER TABLE task   ALTER COLUMN user_id SET DEFAULT :owner_id;
ALTER TABLE review ALTER COLUMN user_id SET DEFAULT :owner_id;

-- 4) 이제 NOT NULL 로 잠근다.
ALTER TABLE plan   ALTER COLUMN user_id SET NOT NULL;
ALTER TABLE task   ALTER COLUMN user_id SET NOT NULL;
ALTER TABLE review ALTER COLUMN user_id SET NOT NULL;

CREATE INDEX plan_user_idx   ON plan (user_id);
CREATE INDEX task_user_idx   ON task (user_id, due_date);
CREATE INDEX review_user_idx ON review (user_id);
```

**되돌리기**: 3)의 DEFAULT 는 인증판 배포 직후 `ALTER TABLE ... ALTER COLUMN user_id DROP DEFAULT;` 로 없앤다.
과제 7 코드는 INSERT 할 때 항상 `user_id` 를 명시하므로 DEFAULT 에 의존하지 않는다.

> 과제 6 자료가 이미 같은 DB 에 있으므로 **별도 가져오기 스크립트는 필요 없다.** 2)의 `UPDATE` 세 줄이 T07-C100 을 충족한다.

## 4. 계층 구조 (MVC + DTO)

과제 요구사항은 아니지만, **"무엇이 어디서 막히는가"를 구조로 설명할 수 있게** 계층을 나눈다. 인증·인가는 흩어지기 쉬운 관심사이고, 흩어지면 한 군데만 빠뜨려도 뚫린다.

```
app/**/page.tsx            View        화면. 서비스 결과를 그리기만 한다
app/api/**/route.ts        Controller  요청 해석 → 세션 확인 → 서비스 호출 → DTO 응답
lib/service/*.ts           Service     업무 규칙과 트랜잭션 경계
lib/repository/*.ts        Repository  SQL. 소유자 조건이 여기에 있다
lib/domain/*.ts            Domain      순수 함수 (기간 계산, 집계 규칙, 검증 규칙)
lib/dto/*.ts               DTO         응답 필드 화이트리스트
lib/db.ts, lib/session.ts  Infra       연결, 세션 발급·조회·폐기
```

### 4-1. 계층 규칙 (어기면 리뷰에서 되돌린다)

| 규칙 | 이유 |
|---|---|
| **Controller 에 SQL 을 쓰지 않는다** | SQL 이 흩어지면 소유자 조건을 빠뜨린 곳이 생긴다 |
| **Repository 는 쿠키·요청·응답을 모르게 한다** | HTTP 를 모르는 계층이라야 테스트에서 그대로 부를 수 있다 |
| **Repository 의 모든 조회·수정·삭제는 `user_id` 를 인자로 받는다** | 소유자 없이 부를 수 있는 함수를 아예 만들지 않는다. **빠뜨릴 자리를 없앤다** |
| **트랜잭션은 Service 에서만 연다** | 계정 삭제처럼 여러 표를 건드리는 일이 한 경계 안에서 끝난다 |
| **응답은 반드시 DTO 를 거친다. DB 행을 그대로 반환하지 않는다** | `SELECT *` 가 새 컬럼을 자동으로 실어 나르는 사고를 막는다 |
| **Domain 은 DB·HTTP 를 import 하지 않는다** | 집계·기간·검증 규칙을 `node --test` 로 바로 검사할 수 있다 |

### 4-2. 출력 DTO

| 함수 | 내보내는 필드 |
|---|---|
| `publicUser(row)` | `id`, `nickname` — **그 밖은 내보내지 않는다** |
| `me(row)` | 본인 계정 화면 전용. `id`, `login_id`, `nickname`, `email`, `created_at` — **`password_hash` 는 절대 포함하지 않는다** |
| `publicPlan` / `publicTask` / `publicRun` / `publicReview` | 화면과 내보내기에 필요한 필드만 화이트리스트로 명시 |

지금 `app/api/export/route.ts` 는 `SELECT *` 를 쓴다. `app_user`·`user_session` 이 생기고 `plan`/`task` 에 `user_id` 가 붙는 순간부터 **`SELECT *` 는 새 컬럼을 자동으로 응답에 실어 나른다.** 필드를 매번 골라 적는 방식은 언젠가 빠뜨리지만, 화이트리스트는 빠뜨릴 수가 없다 (T07-C105 / C106).

### 4-3. 이 구조가 답해 주는 질문

| 질문 | 답 |
|---|---|
| 남의 자료는 어디서 막히나요 | Repository. 모든 함수가 `user_id` 를 인자로 받아 WHERE 에 넣습니다 |
| 화면에서 숨긴 것 아닌가요 | View 는 그리기만 합니다. 차단은 SQL 에서 일어납니다 |
| 비밀번호 해시가 샐 일은 없나요 | 응답은 DTO 화이트리스트만 통과합니다 |
| 규칙은 어떻게 검사했나요 | Domain 이 DB·HTTP 를 모르는 순수 함수라 그대로 단위 검사합니다 |

## 5. 인증 흐름과 소스 위치 (T07-C128)

| 흐름 | 지나가는 소스 |
|---|---|
| **아이디·닉네임 중복확인** | `app/(auth)/signup/page.tsx` 입력 중 → `app/api/auth/check/route.ts` → `lib/service/auth.ts` 의 `isAvailable()` → `lib/repository/user.ts` → 사용 가능 여부만 응답 |
| **가입** | `app/(auth)/signup/page.tsx` → `app/api/auth/signup/route.ts` → `lib/service/auth.ts` 의 `signUp()` → `lib/domain/rules.ts` 의 `checkPasswordRule()` → bcrypt 해시 → `lib/repository/user.ts` 의 `insert()`(유니크 위반 시 409) → `lib/repository/session.ts` 의 `create()` → `lib/dto/user.ts` |
| **로그인** | `app/(auth)/login/page.tsx` → `app/api/auth/login/route.ts` → `lib/service/auth.ts` 의 `signIn()` → `lib/repository/user.ts` 의 `findByLoginId()` → bcrypt 비교 → 세션 발급 |
| **로그아웃** | `app/layout.tsx` 헤더 버튼 → `app/api/auth/logout/route.ts` → `lib/service/auth.ts` 의 `signOut()` → `lib/repository/session.ts` 의 `remove()` (**DB 행 DELETE** + 쿠키 만료) |
| **자료 조회** | 모든 페이지·API → `lib/session.ts` 의 `requireUser()` → `lib/service/*.ts` → `lib/repository/*.ts` (**모든 함수가 `user_id` 를 인자로 받는다**) → `lib/domain/query.ts` 의 `buildTaskWhere()` → `lib/dto/*.ts` |
| **비밀번호 변경** | `app/account/page.tsx` → `app/api/auth/password/route.ts` → `checkPasswordRule()` → 해시 갱신 + 해당 사용자 세션 **전부 DELETE** |
| **계정 삭제** | `app/account/page.tsx` → `app/api/account/route.ts` (DELETE) → `lib/service/account.ts` 의 `deleteAccount()` — **한 트랜잭션** |
| **내보내기** | `app/api/export/route.ts` → `lib/service/account.ts` 의 `exportAll(user_id)` → Repository → DTO |

### 5-1. 새로 만드는 파일

- `schema_auth.sql` — 3-1, 3-2
- `lib/domain/rules.ts` — 아이디·닉네임·비밀번호 규칙 검사 (순수 함수)
- `lib/domain/metric.ts` — 오차율·결측·이상치·반올림 규칙 (순수 함수)
- `lib/service/auth.ts` — 가입·로그인·중복확인·비밀번호 변경, 해시(bcryptjs 위임)
- `lib/service/account.ts` — 내보내기·계정 삭제
- `lib/service/plan.ts` · `task.ts` · `review.ts`
- `lib/repository/user.ts` · `session.ts` · `plan.ts` · `task.ts` · `run.ts` · `review.ts` — **모든 함수가 `user_id` 를 인자로 받는다**
- `lib/dto/user.ts` 외 — 출력 DTO
- `lib/session.ts` — `createSession` / `readSession` / `requireUser` / `destroySession` / `destroyAllSessions`
- `middleware.ts` — 쿠키가 없으면 `/login` 으로 보내는 1차 관문 (**보안 판단은 여기서 하지 않는다**)
- `app/(auth)/login/page.tsx`, `app/(auth)/signup/page.tsx`
- `app/api/auth/` 아래 check · signup · login · logout · password 라우트
- `app/account/page.tsx`, `app/api/account/route.ts`

### 5-2. 고치는 파일

- `lib/query.ts` → **`lib/domain/query.ts` 로 이동**. `buildTaskWhere()` 의 **첫 조건으로 `t.user_id = $1` 을 무조건 넣는다.** 목록·검색·거르기·집계가 모두 이 함수를 지나므로, 여기 한 줄이 목록 누수(T07-C125)를 막는 급소다
- `lib/planner.ts` → **`lib/domain/planner.ts` 로 이동**. 내용은 바꾸지 않는다
- `app/api/plans/**`, `app/api/tasks/**`, `app/api/review/route.ts`, `app/api/export/route.ts` — **SQL 을 Repository 로 옮기고**, Controller 는 세션 확인 → 서비스 호출 → DTO 응답만 한다
- `app/page.tsx`, `app/plans/**`, `app/tasks/**`, `app/review/page.tsx` — 첫 줄에서 `requireUser()` 호출
- `app/layout.tsx` — 로그인한 사용자(닉네임) 표시와 로그아웃 버튼

## 6. 접근 통제 규칙 (T07-C116 ~ C126)

1. **사용자 ID 는 오직 세션에서만 얻는다.** URL 경로·쿼리스트링·요청 헤더·요청 본문의 `user_id`, `owner`, `email` 같은 값은 **읽지 않는다** (T07-C123).
2. **한 건 조회·수정·삭제**는 `WHERE id = $1 AND user_id = $2`. 0행이면 `404`.
   - 부수 효과: 수정·삭제도 같은 WHERE 를 쓰므로 **거절될 때 상대방 자료가 한 글자도 바뀌지 않는다** (T07-C122).
3. **자식 자원**(`run_log`, `task_completion`)은 부모 `task` 를 소유 조건으로 먼저 조회하고, 없으면 `404`.
4. **거절 코드**: 로그인 안 됨 = `401`(API) / `/login` 리다이렉트(화면). 남의 자료 = `404`.
5. **화면에서 숨기는 것은 막은 것이 아니다.** 모든 차단은 서버 라우트의 SQL WHERE 절에서 일어난다.

## 8. 가입 규칙과 계정 문구

### 8-1. 아이디·닉네임 규칙과 중복확인 (T07-C98)

가입은 **아이디 · 닉네임 · 이메일 · 비밀번호** 네 칸을 받는다. 로그인은 **아이디 + 비밀번호**로 한다.

| 항목 | 규칙 |
|---|---|
| 아이디 (`login_id`) | 4~20자, 영문 소문자·숫자·밑줄(`_`)만. 첫 글자는 영문. **대소문자를 무시하고 중복 불가** |
| 닉네임 (`nickname`) | 2~20자, 앞뒤 공백 제거. **대소문자를 무시하고 중복 불가** |
| 이메일 (`email`) | 형식 검사 후 소문자로 정규화. **중복 불가** |

**중복확인은 두 겹으로 한다.**

1. **입력 중 확인(편의)** — 아이디·닉네임 칸에서 포커스가 빠지면 `POST /api/auth/check` 로 물어보고 `사용 가능한 아이디입니다` / `이미 사용 중입니다` 를 그 자리에서 보여준다.
   - 이 응답은 **사용 가능 여부만** 돌려준다. 다른 정보를 함께 돌려주지 않는다.
   - 검사 대상은 아이디와 닉네임뿐이다. **이메일은 이 경로로 확인해 주지 않는다** — 누가 가입했는지 캐낼 수 있기 때문이다.
2. **실제로 막는 것은 DB 유니크 인덱스** — 화면에서 확인한 뒤 제출하기 전에 남이 먼저 가입해 버리는 경우까지 여기서 잡힌다. 위반은 `409`.

> 화면 확인만 믿고 DB 제약을 빼면, 두 사람이 동시에 같은 아이디로 가입하는 순간 중복이 그대로 들어간다.
> **중복확인은 편의이고, 보장은 DB 가 한다.**

### 8-2. 비밀번호 규칙

| 조건 | 값 |
|---|---|
| 최소 길이 | **10자 이상** |
| 영문 대문자 | **1자 이상** (`A-Z`) |
| 영문 소문자 | **1자 이상** (`a-z`) |
| 숫자 | **1자 이상** (`0-9`) |
| 특수문자 | **1자 이상** (영문·숫자·공백이 아닌 문자) |
| 최대 길이 | 128자 (과도한 입력으로 해시 비용이 폭증하는 것을 막는다) |

- 검사는 **`lib/domain/rules.ts` 의 `checkPasswordRule()` 한 곳**에서만 한다. 가입·비밀번호 변경 두 경로가 이 함수를 지난다.
- **화면 검사는 편의일 뿐이고, 서버에서 반드시 다시 검사한다.**
- 위반 시 `400` 과 함께 **어떤 조건이 빠졌는지 알려준다.** 가입 단계에서는 계정 존재 여부가 새지 않으므로 구체적으로 안내해도 안전하다.
- 자동 검사에 조건별로 하나씩 빠진 값이 모두 거절되고, 모두 갖춘 값이 통과하는지 넣는다.

### 8-3. 계정 문구 규칙

- 로그인 실패 문구는 **아이디가 없을 때와 비밀번호만 틀렸을 때가 완전히 같다** (T07-C99):
  `아이디 또는 비밀번호가 올바르지 않습니다.` — 상태코드도 둘 다 `401`.
  계정이 없을 때도 더미 해시로 비교를 한 번 돌려, 응답 시간 차이로 계정 존재 여부가 새지 않게 한다.
- **가입 단계와 로그인 단계의 문구 정책이 다르다.** 가입에서는 무엇이 중복인지 알려 줘도 되지만, 로그인에서는 계정 존재 여부를 절대 알려 주지 않는다.
  - 가입 중복: `이미 사용 중인 아이디입니다.` / `이미 사용 중인 닉네임입니다.` / `이미 가입된 이메일입니다.` — 모두 `409`
- **비밀번호는 로그에 절대 남기지 않는다** (T07-C105 / C106). 규칙 위반 응답에도 입력한 값을 되돌려주지 않는다.

## 11. 아직 못 막은 것 (T07-C130 초안)

구현 후 실제 상태로 확정한다. 현재 계획상 **하지 않기로 한 것**:

- **로그인 수단은 비밀번호 하나** — 아이디·비밀번호 찾기는 가입 시 등록한 닉네임·이메일·아이디의 일치로만 복구하며 별도 2차 인증은 없다.
- **무차별 대입(brute force) 방어 없음** — 로그인 시도 횟수 제한·계정 잠금·CAPTCHA 가 없다. 비밀번호 복잡도 규칙(8-2)이 추측 난이도를 크게 올려 주지만 **시도 자체를 막지는 못한다.**
- **유출된 비밀번호 목록 대조 없음** — 복잡도 조건은 갖췄지만 이미 유출된 흔한 비밀번호(`Password1!` 같은)는 그대로 통과한다.
- **이메일 소유 확인 없음** — 메일 발송 수단이 없어 복구는 등록 정보 일치 방식이다. 비밀번호 재설정 시 기존 세션은 전부 폐기하지만, 운영 서비스라면 이메일 일회용 링크로 교체해야 한다.
- **두 번째 인증 수단(2FA) 없음**
- **보안 이벤트 로그 없음** — 침입이 일어나도 알아차릴 수 없다.
- **CSRF 토큰 없음** — `SameSite=Lax` 쿠키에만 의존한다.
- **중복확인 API 로 아이디·닉네임 존재 여부를 캐낼 수 있음** — 호출 횟수 제한을 두지 않았다. 이메일은 이 경로에서 확인해 주지 않아 피해 범위를 줄였다.
- **인증판 배포 전까지 과제 6 주소에서 자료가 공개된다** — 같은 DB 를 쓰기 때문이다 (0-1 참조).
