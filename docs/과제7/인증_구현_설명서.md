# 인증 구현 설명서 — 잠긴 플랜두씨 다이어리

> 검증 기록에는 아이디·이메일·비밀번호·세션 쿠키·DB 접속 문자열 원문을 남기지 않았다. 일회성 검증 계정과 자료는 검증 직후 삭제했다.

## ① 무엇으로 붙였는가

- 인증 방식: 직접 구현한 **서버 DB 세션**
- 비밀번호 처리: **bcrypt**, `bcryptjs 3.0.3`, cost 12
- 앱: Next.js 16.3.3
- 로그인 입력: 아이디와 비밀번호

브라우저에는 예측하기 어려운 불투명 세션 값을 `HttpOnly` 쿠키로 보내고, DB에는 그 값의 SHA-256 해시와 7일 만료 시각만 저장한다. 비밀번호는 복호화할 수 없는 bcrypt 해시로만 저장한다.

## ② 왜 이 방법을 골랐는가

bcryptjs는 계정마다 임의 소금값을 자동으로 포함하고 서버리스에서 네이티브 모듈 빌드가 필요 없다. DB 세션은 로그아웃이나 비밀번호 변경 즉시 서버에서 행을 지워 이전 세션을 폐기할 수 있다.

검토했지만 선택하지 않은 방법:

- Auth.js Credentials: 현재 구성의 JWT 세션은 즉시 폐기 요구에 맞추기 어렵다.
- Supabase Auth: 액세스 토큰 만료 전 즉시 차단을 별도로 설계해야 한다.
- express-session: Next.js App Router에 별도 서버·저장소 어댑터를 더해야 한다.

## ③ 가입·로그인·로그아웃·자료 조회 흐름

| 흐름 | 화면/API | 핵심 소스 |
|---|---|---|
| 가입 | `/signup` → `POST /api/auth/signup` | `app/(auth)/signup/page.tsx` → `app/api/auth/signup/route.ts` → `lib/service/auth.ts` → `lib/repository/user.ts` |
| 로그인 | `/login` → `POST /api/auth/login` | `app/(auth)/login/page.tsx` → `app/api/auth/login/route.ts` → `lib/service/auth.ts` → `lib/session.ts` |
| 로그아웃 | `POST /api/auth/logout` | `app/api/auth/logout/route.ts` → `lib/session.ts` → `lib/repository/session.ts` |
| 자료 조회 | `/tasks` 또는 `GET /api/tasks` | `middleware.ts`·`lib/session.ts`에서 로그인 확인 → `lib/domain/query.ts`와 라우트 SQL에서 세션의 `user_id` 조건 적용 → `lib/dto/records.ts`로 응답 제한 |

사용자 ID는 URL·헤더·요청 본문에서 받지 않고 검증된 세션에서만 정한다. 한 건 조회·수정·삭제도 `id`와 `user_id`를 함께 조건으로 사용해 남의 자료 존재를 드러내지 않는 `404`를 반환한다.

| 확인 | 성공 요청 | 차단·대조 요청 | 결과 |
|---|---|---|---|
| 1. 미로그인 차단 | 로그인 후 `GET /api/tasks` → 200 | 미로그인 `GET /api/tasks` → 401, 브라우저 `/tasks` → `/login` 307 | 통과 |
| 2. 비밀번호 저장 | 같은 비밀번호로 일회성 계정 2개 가입 → 201 | DB 저장 모양 `$2b$12$…`(각 60자), 두 값 비교 | 원문 없음·서로 다름, 통과 |
| 3. 세션 폐기 | 로그아웃 전 같은 주소 → 200, 변경한 비밀번호 로그인 → 200 | 로그아웃 뒤 이전 세션 → 401, 비밀번호 변경 뒤 이전 세션·이전 비밀번호 → 401 | 통과 |
| 4. 계정 간 자료 격리 | 각 일회성 계정이 자기 계획·할 일 생성 → 201 | 양방향 타 계정 읽기·수정·삭제 → 모두 404 | 대상 행 수와 내용 불변·목록 유출 0건, 통과 |
| 5. 가입·로그인 문구 | 서로 다른 계정 가입 → 201 | 중복 가입 → 409, 틀린 비밀번호와 없는 아이디 → 같은 401 문구 | 통과 |

검증용 아이디·비밀번호·세션 값은 저장하지 않았으며, 검증용 계정과 연결 자료는 마지막 단계에서 외래키 연쇄 삭제로 정리했다. 사용자가 직접 입력한 기존 계획 2개·할 일 5개·돌아보기 1개는 소유자 계정으로 귀속한 뒤 그대로 유지했다.

## ⑤ 세션·저장·보안 세부 규칙

- 세션 쿠키: `HttpOnly`, `SameSite=Lax`, 배포 환경에서 `Secure`, 유효기간 7일
- 서버 저장: 세션 원문이 아니라 SHA-256 해시만 `user_session`에 저장
- 비밀번호: bcrypt cost 12, 응답 DTO와 로그에서 제외
- 중복 방지: 아이디·닉네임·이메일의 대소문자 무시 유니크 인덱스
- 소유권: `plan`, `task`, `review`의 `user_id NOT NULL`; 목록·검색·집계와 단건 변경 모두 적용
- 세션 폐기: 로그아웃은 현재 세션 삭제, 비밀번호 변경은 해당 사용자의 모든 세션 삭제

## ⑥ 아직 못 막은 것과 위험

- 로그인 시도 횟수 제한·계정 잠금·CAPTCHA가 없다. 강한 비밀번호 규칙은 추측 난도를 높이지만 무차별 대입 시도 자체를 막지 못한다.
- 중복확인 API에 호출 횟수 제한이 없어 아이디·닉네임 존재 여부를 반복 조회할 수 있다. 이메일은 이 API에서 확인해 주지 않아 범위를 줄였다.
- 비밀번호 찾기·이메일 소유 확인은 아직 없다. 이메일 오입력 시 자동 복구가 불가능하다.
- 관리자용 세션 강제 종료·감사 로그가 없다. 계정 이상 징후를 운영자가 추적하기 어렵다.

과제 7의 핵심인 가입·로그인·즉시 세션 폐기·자료 소유권 차단을 우선 구현했으며, 위 항목은 실제 공개 운영 규모가 커질 때 추가한다.
