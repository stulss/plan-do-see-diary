# 5일 사용 기록 — 잠긴 플랜두씨 다이어리

> 2026-09-02 문서 최신 확인 완료. 앱·DB·배포 검증은 끝났으며, 아래 실제 날짜·수치·판단만 사용자가 5일 동안 직접 기록한다.

> 잠근 앱을 **실제로 5일 동안 쓰면서** 남기는 기록이다.
> **2일차 기록 뒤 · 3일차 기록 앞**에 계획 규칙을 **딱 하나만** 바꾼다.
> 기록은 모두 **내 계정 안에** 들어 있어야 한다 (T07-C07).

## 1. 1일차에 한 번만 정하는 것 (T07-C04 ~ C06, C08)

아래 다섯 칸은 **1일차에 고정하고 5일 내내 바꾸지 않는다.** 바꾸는 것은 §3의 계획 규칙 하나뿐이다.

| 고정 항목 | 값 |
|---|---|
| **답하려는 질문 한 문장** (C04) | 하루에 계획한 시간과 실제로 쓴 시간의 차이를, 계획 규칙을 바꿔서 줄일 수 있는가? |
| **볼 지표 한 개** (C05) | **하루 시간 오차율** |
| **지표의 단위** (C06) | **퍼센트(%)** — 원자료 단위는 **분(minute)** |
| **계산 규칙** (C08) | `하루 시간 오차율(%) = (그날 완료한 할 일의 실제 분 합 − 예상 분 합) ÷ 예상 분 합 × 100` |
| **대상 범위** | Asia/Seoul 기준 **그 날짜에 완료 표시된 할 일**만. 예상 분은 `task.estimate_minutes`, 실제 분은 그 할 일의 `run_log.actual_minutes` 합 |

### 자잘한 규칙 (T07-C23 ~ C27)

| 상황 | 처리 방법 |
|---|---|
| **값이 빠졌을 때** (C23) | 예상 분 또는 실제 분이 없는 할 일은 **분자·분모 양쪽에서 모두 제외**하고 "미기록 n건"으로 따로 센다. 예상 분 합이 0이면 오차율은 **"계산 불가"** 로 적는다 |
| **값이 중복될 때** (C24) | 같은 할 일에 같은 시작 시각으로 들어온 실행 기록은 **가장 먼저 만들어진 1건만** 센다. 완료 기록은 DB 기본키가 `task_id` 라 이미 1건만 존재한다 |
| **값이 유난히 튈 때** (C25) | 실행 기록 1건의 실제 분이 **480분(8시간)을 넘으면 이상치로 표시(⚠)** 하되 **합계에는 포함**하고, 그날 칸에 사유를 적는다. 자료를 조용히 빼지 않는다 |
| **반올림** (C26) | 오차율(%)은 **소수점 첫째 자리에서 반올림**. 분 합계는 정수 그대로 두고 반올림하지 않는다 |
| **주 시작 요일** (C27) | **월요일** (`lib/domain/planner.ts` 의 `startOfWeek()` 에 구현되어 있음) |

### 1일차에 정한 계획 규칙 (변경 전)

> **계획 규칙**: 하루에 계획하는 할 일은 **3건까지**, 각 할 일의 예상 시간은 **60분 이하**로 잡는다.

## 3. 계획 규칙 변경 (T07-C09 ~ C12)

> **위치가 채점 대상이다.** 이 절은 반드시 **2일차 기록 뒤 · 3일차 기록 앞**에 있어야 한다.

| 항목 | 값 |
|---|---|
| **바꾼 시각** (C10) | `(YYYY-MM-DD HH:MM, Asia/Seoul)` |
| **가리키는 근거** (C12) | 위 **1일차 `(YYYY-MM-DD)`** 기록과 **2일차 `(YYYY-MM-DD)`** 기록 |
| **바꾸기 전 규칙** | 하루 할 일 3건까지, 각 할 일 예상 시간 **60분 이하** |
| **바꾼 뒤 규칙** | 하루 할 일 3건까지, 각 할 일 예상 시간 **90분 이하** |
| **무엇을 하나만 바꿨나** | 예상 시간 상한 **60분 → 90분**. 건수 상한(3건)과 지표·단위·계산 규칙은 그대로 둔다 |
| **바꾼 이유** (C11) | `(기입 — 1·2일차 오차율을 근거로 한 문장)` |

> ⚠️ 지표·단위·계산 규칙은 **바꾸지 않는다.** 그래야 전후 비교가 성립한다 (T07-C13 ~ C15).
