# 트러블슈팅

실제로 겪은 문제만 기록한다. 겪지 않은 문제를 미리 지어내지 않는다.

## 기록 형식

```
### (날짜) 제목
- 증상: 무엇이 어떻게 잘못 보였는가
- 시도: 무엇을 해봤는가 (실패한 시도 포함)
- 비교: 어떤 선택지를 저울질했는가
- 해결: 무엇이 원인이었고 어떻게 고쳤는가
- 배운 점: 다음에 같은 상황에서 무엇을 먼저 볼 것인가
```

## 기록

### 2026-08-31 초기 Next.js 버전의 보안 감사 실패

- 증상: 최초 설치한 Next.js 14.2.31에서 `npm audit` 고위험 취약점이 보고됐다.
- 시도: 같은 메이저의 최신 14.2.35와 Next.js 15.5.21 범위를 비교했지만 최신 보안 권고를 모두 해소하지 못했다.
- 비교: 구버전 API 호환성을 유지하는 선택과 보안 패치가 끝난 현재 버전으로 올리는 선택을 비교했다.
- 해결: Next.js 16.3.3으로 올리고 비동기 `params`/`searchParams` 타입을 맞췄다. 재감사 결과 취약점 0건, production build 통과.
- 배운 점: 새 프로젝트는 설치 직후 감사 결과를 확인하고, 과거 고정 버전보다 현재 패치 버전을 우선한다.

### 2026-08-31 Supabase에서 내보내기 API가 30초 지연됨

- 증상: 일반 화면과 API는 즉시 열렸지만 `/api/export`만 빈 DB에서도 약 30초가 걸렸다.
- 시도: 같은 여섯 조회를 직접 연결에서 순차 실행과 병렬 실행으로 나누어 비교했다.
- 비교: 순차 조회는 약 0.3초에 끝났고, 여섯 병렬 조회는 무료 Supabase 연결 풀에서 30초 이상 대기했다.
- 해결: 내보내기 조회를 순차 실행으로 바꿔 연결 하나를 재사용했다.
- 배운 점: 작은 표 몇 개를 한 번 내보내는 경로에서는 연결 수를 늘리는 병렬화보다 순차 조회가 더 빠르고 안정적이다.

### 2026-08-31 Supabase 풀러에서 prepared statement가 간헐적으로 사라짐

- 증상: 화면을 여러 번 새로고침할 때 `prepared statement ... does not exist`와 버퍼 offset 오류가 간헐적으로 발생했다.
- 시도: 개발 서버를 새로 시작하면 잠시 정상화됐지만 여러 화면을 연속 조회하면 다시 나타났다.
- 비교: 쿼리마다 재연결하는 방법과 기존 연결 풀을 유지하되 prepared statement만 끄는 방법을 비교했다.
- 해결: Supabase 트랜잭션 풀러가 요청 사이의 물리 연결과 statement를 보존하지 않는 것이 원인이었다. Postgres.js 연결에 `prepare: false`를 지정해 일반 쿼리로 실행했다.
- 배운 점: 트랜잭션 풀러를 쓰는 관리형 PostgreSQL에서는 서버 재시작보다 클라이언트의 prepared statement 호환 설정을 먼저 확인한다.

### 2026-09-01 제출 보고서에 검증안내서 내용이 빠짐

- 증상: 사용자가 수정한 15장 PPT에는 `docs/검증안내서.md`의 확인 방법 4줄과 항목별 통과 기준이 들어 있지 않았다.
- 시도: 기존 생성 스크립트를 다시 실행하면 사용자가 직접 고친 디자인과 문구가 덮어써질 수 있어 재생성하지 않았다.
- 비교: 보고서 전체 재생성과 기존 수정본에 필요한 슬라이드만 추가하는 방법을 비교했다.
- 해결: 사용자 수정본을 별도 백업하고 마지막 제출 슬라이드 앞에 검증안내서 3장을 추가한 뒤, 18쪽 PDF로 다시 내보냈다. 기존 15장의 텍스트가 그대로인지도 비교했다.
- 배운 점: 사람이 수정한 산출물은 원본을 보존하고, 누락된 범위만 추가한 뒤 슬라이드 수·핵심 문구·PDF 페이지 수를 함께 검사한다.

## 미리 예상되는 함정 (겪으면 위 형식으로 옮겨 적을 것)

- 집계 숫자와 되짚어 간 목록 건수가 어긋남 → 조건을 두 곳에 따로 쓴 게 원인일 가능성이 높다
- 지연 수가 하루 어긋남 → 마감일 비교를 UTC 기준으로 하고 있지 않은지 확인
- 예상/실제 차이가 이상함 → 한쪽을 시간, 한쪽을 분으로 저장하고 있지 않은지 확인
- 완료가 두 번 기록됨 → 버튼 비활성화만으로 막고 있고 DB 제약이 없는 경우
